# Account Management implementation and verification

This change adds configurable administrative accounts using the existing User, credentials login, bcrypt password hashing, status/session revocation, audit, navigation and business services. It does not create a parallel authentication system.

## Verified owner

A SELECT-only inspection of the configured production database found exactly one existing Super Admin: login `admin`, stable User ID `cms7ic4rj0000x82oim91juta`, active and not deleted, created 2026-07-30. Authentication uses the User ID from the signed session. Ownership is bound to that verified ID in a singleton AccountManagementOwner record. Username, designation, client role and client permissions never establish ownership. No production records were changed.

The existing temporary passwordless admin-bypass provider is enabled in the configured local environment. Account Management rejects bypass sessions and older sessions without the trusted authentication-method claim. The owner must sign out and log in with normal credentials. Alternate user APIs cannot reset the owner's password through that bypass or deactivate, delete or reassign the owner. The existing bypass remains unchanged for other modules; its deployed environment flag was not independently verified.

## Account and permission model

- CUSTOM_ADMIN is a separate internal role. Free-text designation is presentation only.
- User.designation is nullable; User.adminPermissions is explicit module-to-action JSON with a default empty object. Existing role permissions remain in the original role matrix.
- Create/edit validates names, the existing username format, password length, status and known module/action combinations. Passwords use bcrypt (cost 10); DTOs and audits contain no password hashes or plaintext passwords.
- Only the bound owner can create/edit/list custom accounts, reset their passwords or change their status/grants. Alternate employee-management APIs cannot mutate custom accounts or let them mutate Super Admin accounts.
- Account updates and their audit records are transactional. Edits lock the target row so audit before/after is accurate. Status/password changes revoke prior sessions through sessionValidAfter. Custom grants, current role and active/deleted state are read from the database on every protected request, without the legacy auth TTL or JWT permission snapshots.
- New AuditLog, ApprovalAction and CnPaymentEvent rows optionally snapshot the actor designation. Historical rows remain null; historical titles are never inferred from current profiles. Existing actor IDs, dates, status transitions and calculations are retained.

## Enforcement and presentation

The permission catalogue follows existing navigation leaves and actual API operations. Account Management is not grantable. CUSTOM_ADMIN navigation shows only permitted pages; its badge/profile show its designation. Each server page invokes authorization, including pages formerly relying only on a persistent layout. Middleware supplies the real request pathname and method, overwriting client headers. Both named/default middleware exports use the same wrapper. The server checks module access plus the operation grant; unknown endpoints/pages are closed to custom administrators. Internal administrative-category checks do not themselves grant authority.

Payload-dependent decisions are additionally checked in their authoritative services: CN accept/reject/post/verify, dealer-tag assign/revoke/decide, plan approve/reject/return, month-extension decisions and lifecycle restore. Paid CN verification also requires the posting grant. Existing approval, financial-state, status and ownership checks still run after permission checks. Original SO/RM and Super Admin business branches remain intact.

Approvals visibility/action grants and the relevant planning module/action must both be assigned for planning approvals/returns. CN actions use CN Requests grants; Dealer Tags use Dealer Tags grants. Payments and planned installment edits retain separate Payments/payment and Scheme Planning/update grants. Read-only access does not enable writes.

Existing shared selector APIs remain available for their consuming screens: report/planning season choices, planning/import officer choices, active tag choices, groups, categories, resource and assignment options, dealer display metadata and resolved labels. Exact season/assignment/tag reads do not grant access to their management pages or mutations. Tests explicitly check this distinction.

## Existing workflows deliberately not delegated

Employee-owned plan submission, ordinary owner-only plan editing, Scheme dealer-plan creation/conversion, personal Daily Work planning/actuals/finalization, SO CN task/payment updates and RM team reviews retain their existing role/ownership rules. Custom administrators use the existing administrative viewer/edit/approval operations where those exist. No employee identity is impersonated.

Team Performance is an RM-specific screen, so it is not a grantable administrative module; company Performance is grantable. Cross-module global search is hidden and denied for custom administrators because its existing results have no module-level filtering. The legacy generic Users resource API is denied to custom administrators because it permits role changes and exposes hashes; the existing employee-management API/UI is reused instead. Shared selectors expose their existing reference data, not a second management workflow.

Review is separately grantable for existing Dealer Import resolve and Price Import preview endpoints. Other upload workflows stage review client-side and gate their consequential analyze/import endpoints; no artificial review endpoint was added. Some legacy administrative controls may remain visible, but the server independently denies any ungranted operation. This change does not redesign those screens.

## Migration prepared for review only

prisma/migrations/20261003000000_account_management/migration.sql adds CUSTOM_ADMIN, User designation/grants, the singleton owner binding and nullable designation snapshots for the three history models. The owner insert targets only the verified stable ID and requires an active, nondeleted Super Admin. Environments without that ID remain unbound/closed; they need an independently verified owner rather than automatic username/creation-order inference.

The migration was applied only to the disposable PostgreSQL database at 127.0.0.1:55442/account_management_test to validate schema and integration behavior. It has NOT been applied to production. No production writes, configuration edits, historical title backfills or permission grants were performed. Review/apply the migration through the deployment process before running the updated application against production; the new queries require the added fields/table. Normal owner credentials login is then required for Account Management.
